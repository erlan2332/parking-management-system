# Журнал решений и реального процесса разработки

**Проект:** Parking Management System — веб-сервис платной парковки  
**Период основной разработки:** 20–21 октября 2026 года  
**Подход:** поэтапная разработка с помощью ChatGPT (планирование и формулирование задач) и Codex (изменение кода, запуск проверок, подготовка коммитов и pull request). Решения и результаты проверялись по коду, тестам и поведению приложения.

> Это не полный протокол всех сообщений агента и не перечень «идеальных» решений задним числом. Здесь зафиксированы реальные технические выборы, проблемы, изменения требований и компромиссы. Подробная последовательность реализации находится в `DEVELOPMENT_LOG.md`, а исходные задания — в сохранённой истории Codex. Даты ниже взяты из истории разработки; точное время отдельных коммитов нужно смотреть в Git.

## 1. Почему Java и Spring Boot, а не Python, Go или Node.js

В задании работодателя Python, Go и Node.js названы **предпочтительными, но не обязательными** вариантами Backend. Мы осознанно выбрали **Java 21 и Spring Boot**, поскольку основной акцент проекта — корректная бизнес-логика бронирования, конкурентные операции и работа с реляционной БД. Spring предоставляет готовые механизмы транзакций, валидации, безопасности и интеграции с PostgreSQL. Использование знакомого стека позволяло уделить больше времени требованиям парковки, а не освоению нового инструментария.

При этом архитектура осталась клиент-серверной: Spring Boot — отдельное приложение с REST API и WebSocket, React — отдельный клиент. Выбор Java не меняет контракт взаимодействия между ними.

Для Frontend выбрали **React + TypeScript + Vite** (React входит в разрешённые технологии), для БД — **PostgreSQL**, для сборки Backend — Gradle. Локально решили запускать сервисы **без обязательного Docker**. В GitHub Actions контейнер PostgreSQL используется только как воспроизводимое окружение проверок.

## 2. Разрабатывать по этапам, а не генерировать всю систему одним запросом

**Решение.** Разделили работу на последовательные этапы: БД и миграции → пользователи и автомобили → авторизация → карта мест → бронирование → шлагбаум и визиты → тарифы → счета → автоматизация → WebSocket → стабилизация и рефакторинг → Frontend.

**Почему.** Так проще проверить каждый слой перед следующим, обнаружить ошибку в конкретном изменении и показать работодателю реальный ход работы. Для этапов использовали отдельные коммиты и pull request в ветку `dev-parking`; слияние выполнялось отдельно.

**Как это выглядело на практике.** В истории Codex есть повторные команды «продолжай», а на этапе тарификации агент сначала попросил объединить предыдущий PR. Мы не пытались незаметно обойти зависимость: после сообщения о слиянии вернулись к тарифам. При переходе к Frontend выяснилось, что рефакторинг Backend ещё не закончен. Задание на Frontend было остановлено словами «я поторопился, сначала закончи полностью прошлый»; к клиентской части вернулись после завершения предыдущего этапа.

## 3. PostgreSQL и Flyway: не позволять ORM незаметно менять схему

**Решение.** Использовали PostgreSQL, миграции **Flyway V1–V7**, `spring.jpa.hibernate.ddl-auto=validate`. Первые миграции создают парковочные места `A1–A10` и `B1–B10`. Уже применённые миграции не редактировали: изменения добавлялись следующими версиями.

**Почему.** Структура БД должна воспроизводиться на чистом окружении и не зависеть от действий Hibernate. Уникальные ограничения, индексы и правила целостности особенно важны при одновременных запросах.

**Через что прошли.** На ранней настройке возникали проблемы с подключением тестов к PostgreSQL. Позже отдельно прогнали установку с пустой БД, проверили применение семи миграций, наличие 20 мест и повторный запуск без дублирования данных. Рабочую и тестовую БД отделили друг от друга; обязательные переменные подключения стали явными, чтобы случайно не работать с чужой локальной базой.

## 4. Пользователи, автомобили и безопасность данных

**Решение.** Сделали регистрацию и вход, хотя по ТЗ они необязательны. Использовали **Spring Security**, JWT и BCrypt вместо самописной криптографии и фильтров. Идентификатор владельца берётся из проверенного JWT, а не передаётся клиентом как доверенное значение.

Номер автомобиля приводится к единому виду; его уникальность и уникальность email без учёта регистра обеспечиваются в PostgreSQL. Проверка в Java даёт понятную ошибку, но именно ограничение БД защищает от гонки параллельных запросов.

**Через что прошли.** Исправляли порядок нормализации email и валидации входных данных; проверяли некорректные и просроченные JWT, доступ к чужим автомобилям и конкурентную регистрацию. Отдельно сделали явную ошибку запуска, если отсутствует или неверно настроен `JWT_SECRET_BASE64`. Пароли и хэши не возвращаются в API.

## 5. Состояние места вычисляется из фактов, а не хранится отдельным флагом

**Решение.** Не заводили вручную обновляемое поле `occupied` в таблице парковочных мест. Текущее состояние определяется из активных визитов, бронирований, временных удержаний и признака доступности места.

**Почему.** Иначе при сбое в одном из сценариев записи могли бы противоречить друг другу: например, визит активен, а место в таблице помечено свободным. Физическая занятость имеет приоритет над отображением брони. Интервальная доступность рассчитывается для периода, выбранного клиентом.

**Компромисс.** Отдельной аппаратной модели датчиков нет: симуляция занятости опирается на операции въезда и выезда. Это указано в README как ограничение.

## 6. Самая рискованная часть: два пользователя бронируют одно место

**Проблема.** Обычная последовательность «проверить свободно ли место → записать бронь» не защищает от двух запросов одновременно: оба могут увидеть свободное место.

**Решение.** Ввели трёхминутное временное удержание и подтверждение брони. Удержание и подтверждённая бронь находятся в одной таблице `reservations`: подтверждение меняет статус существующей записи, не открывая промежуток между удалением одного объекта и созданием другого.

Защиту от пересекающихся периодов обеспечивают **PostgreSQL exclusion constraints** с `btree_gist` и полуоткрытым интервалом `[startAt, endAt)`. Ограничения работают и для одного места, и для одного автомобиля. В операциях используются транзакции и блокировки строк с согласованным порядком захвата.

**Почему именно так.** Java-проверки полезны для сообщений об ошибках, но не являются гарантией при конкурентной работе. Решение должно сохранять корректность и при двух браузерах, и при двух одновременных запросах к серверу.

**Проверки.** Добавили тесты с независимыми транзакциями, проверку истечения удержания и невозможности его подтвердить после срока. Удаление просроченных удержаний выполняется не только по таймеру: важные запросы учитывают истечение сразу, чтобы задержка планировщика не блокировала место.

## 7. Въезд без брони, повторный въезд и конкурентный выезд

**Решение.** Источником фактического нахождения машины на парковке сделали `parking_visits`. Въезд по брони связывает визит с подтверждённой бронью; для автомобиля без брони система выбирает подходящее свободное место. Блокировки и уникальные индексы PostgreSQL не позволяют открыть два активных визита на один автомобиль или место.

**Почему был нужен осторожный алгоритм walk-in.** Время будущего выезда неизвестно. Поэтому при автоматическом выборе нельзя занимать место, для которого уже существуют обязательства по будущим броням или удержаниям. Сервис повторно проверяет доступность **после** блокировки строки, а не доверяет устаревшему предварительному списку.

**Проверки и компромиссы.** Рассмотрены два въезда подряд, выезд без активного визита, одновременный въезд и бронирование, параллельные выезды. Для корректной последовательности операций придерживаемся порядка блокировок «место → автомобиль → связанная бронь/визит».

## 8. Тарифы: считать по секундам и не округлять каждый участок отдельно

**Решение.** Тарифная зона — **Asia/Bishkek**, день — **08:00–20:00**, ночь — **20:00–08:00**. По умолчанию дневная ставка составляет **2 KGS/мин**, ночная — **1 KGS/мин**. Длительность рассчитываем по фактическим моментам въезда и выезда, разделяем по границам тарифов и считаем через `BigDecimal`.

**Почему.** Наивный подсчёт «количество начатых минут × тариф» или отдельное округление каждого отрезка даёт неверный итог при пересечении 20:00, 08:00 или полуночи. Сначала суммируем точные составляющие, затем **один раз** округляем общую сумму до двух знаков (`HALF_UP`).

**Проверки.** Разбирали границы тарифов, переход через несколько суток, различные UTC-смещения и дробные секунды. Логику расчёта оставили независимой от HTTP и БД, чтобы тестировать её отдельно.

## 9. Счёт должен сохранять историческую стоимость

**Проблема.** Если при каждом открытии истории пересчитывать сумму по текущим тарифам, старый визит может «подорожать» после изменения настроек.

**Решение.** При выезде сохраняется отдельный счёт со снимком исходного интервала, ставок, длительностей и суммы. Завершение визита и создание счёта происходят **в одной транзакции**: если запись счёта не удалась, выезд тоже откатывается. Уникальная связь с визитом предотвращает повторное начисление.

**Результат.** Чтение истории не создаёт новых счетов. Повторные вызовы и конкурирующие попытки выезда проверялись отдельно. Реальная онлайн-оплата и PDF-счёт не реализованы — по текущему объёму проекта требуется формировать итоговый счёт, а не подключаться к банку.

## 10. No-show через 15 минут и Email-напоминания

**Решение.** Если водитель не въехал, бронь перестаёт действовать через 15 минут от начала либо раньше, если бронирование заканчивается до этого момента. Это правило едино для входа через шлагбаум, поиска доступных мест и фоновой очистки.

Для напоминания за 10 минут до окончания действующего посещения использован **notification outbox**: состояние заявки на письмо хранится в PostgreSQL, обработчик забирает её и использует SMTP только при включённой настройке. В CI вместо реальной почты работает тестовый отправитель.

**Честное ограничение.** Уникальность записи и захват задания защищают от обычной повторной обработки, но **строго гарантировать однократную доставку SMTP невозможно** при сбое между принятием письма почтовым сервером и фиксацией статуса отправки в БД. Поэтому в документации не заявляем невозможной гарантии. SMTP по умолчанию отключён; для проверки можно подключить Mailpit.

## 11. Обновление карты у двух пользователей без перезагрузки

**Решение.** Использовали **WebSocket/STOMP** с JWT в заголовке `CONNECT`. Сервер публикует небольшое событие о том, какое место изменилось. Получив событие, React заново запрашивает актуальное состояние через REST.

**Почему не передавать по WebSocket всю карту.** Иначе пришлось бы поддерживать два механизма расчёта занятости и синхронизировать клиентское состояние вручную. PostgreSQL остаётся источником истины, WebSocket служит сигналом «данные изменились».

**Сложность, которую учли.** Событие должно уходить **после успешного коммита**, иначе пользователь может увидеть изменение, которое затем откатилось. Для этого применён обработчик событий `AFTER_COMMIT`. Проверяли две STOMP-сессии, авторизацию, отклонение недопустимых действий и переподключение.

**Ограничение.** Встроенный брокер ориентирован на один экземпляр Backend и не воспроизводит события, пропущенные при отключении. После переподключения клиент синхронизируется через REST.

## 12. Стабилизация: тесты выявили проблему CORS

После реализации основных возможностей мы отдельно проверяли связку React и Spring Boot, а не полагались только на запуск Backend. Выяснилось, что WebSocket Origin контролируется, но **CORS для обычных REST-запросов из браузера не настроен**. Это могло мешать Frontend, даже если API корректно отвечал из терминала.

**Исправление.** Добавили явный список разрешённых Origin для REST, отдельно от WebSocket; разрешили нужные методы и заголовки и написали тесты на preflight. Одновременно убрали неявные значения подключения к БД. Проверили запуск на чистом PostgreSQL, регистрацию, бронь, въезд, выезд и историю счетов.

По журналу этого этапа полный набор Backend-тестов прошёл **159/159**, а выделенные smoke-тесты — **22/22**. Это результаты указанного этапа, а не обещание, что любые будущие версии кода автоматически проходят те же проверки.

## 13. Рефакторинг: сначала работоспособность, затем структура

**Проблема.** По мере добавления бронирований, шлагбаума и счетов отдельные сервисы стали слишком объёмными. Возникла потребность привести пакеты к единой структуре и убрать смешение обязанностей.

**Решение.** По отдельному заданию **№11-R** нормализовали пакеты по бизнес-модулям и ответственности: `controller`, `dto`, `mapper`, `service`, `repository`, `entity`, `model`, `config`. Мапперы преобразуют данные в DTO, но не обращаются в репозитории и не принимают бизнес-решений; сервисы содержат сценарии и границы транзакций.

Lombok добавили **выборочно** для повторяющегося кода, но не стали использовать `@Data` для JPA-сущностей или скрывать им конструкторы с важной валидацией. Не создавали пустые пакеты, интерфейсы «один интерфейс — одна реализация», CQRS и другие слои только ради видимости SOLID.

**Что нельзя было сломать.** Публичные REST-адреса и JSON-поля, JWT, сроки удержаний, цены и округление, сохранённые счета, WebSocket, Flyway V1–V7, порядок блокировок и атомарность выезда. После рефакторинга журнал фиксирует **160/160 Backend-тестов** и **22/22 smoke-теста**.

## 14. React Frontend: не просто макет, а работа с реальным Backend

**Решение.** Создали отдельное приложение на React, TypeScript, Vite и Tailwind. Компоненты разделили по функциям: профиль, автомобили, карта парковки, бронирования, шлагбаум, визиты, счета. Запросы и обновление серверных данных организовали через типизированный API-клиент и TanStack Query.

**Сложности.** Нужно было учитывать выбранный временной интервал во всех запросах карты, отсчитывать удержание от серверного `holdExpiresAt`, обрабатывать `409 Conflict`, переподключать WebSocket и не допускать устаревшей карты после действий другого пользователя. В журнале записана проверка двух независимых сессий браузера, в которых удержание и освобождение места обновлялись без перезагрузки.

**Проверки.** Frontend получил собственные lint/typecheck/test/build в GitHub Actions. Проверяли интерфейс на широком и узком экранах; в частности, устраняли горизонтальное переполнение карточки счёта на мобильной ширине.

## 15. Последние исправления интерфейса — по фактической обратной связи

Это не были изменения «для галочки». После первого рабочего варианта интерфейса мы увидели неудобства и несколько раз возвращались к одному и тому же пользовательскому сценарию:

- **21 октября, 21:24 (Asia/Bishkek):** попросили удалить лишние поясняющие надписи со страниц. Решение — оставить только информацию, нужную для действия пользователя.
- **21 октября, 21:34:** подтверждение временного удержания переделали в **модальное окно** с обратным отсчётом и убывающей полосой времени. Пользователь должен явно подтвердить бронь.
- **21 октября, 21:41:** при выборе места появлялось сообщение, сдвигавшее блок над картой; также в модальном окне дублировалось отображение времени. Убрали лишний текст и повторяющиеся элементы.
- **21 октября, 21:47:** длинная подпись места в состоянии удержания меняла размеры плитки. Сократили надпись и зафиксировали высоту, чтобы карта не «прыгала».
- **21 октября, 22:27:** убрали оставшиеся поясняющие блоки со страницы входа.

Эти эпизоды есть в сохранённой переписке с Codex. Они показывают реальный цикл разработки: **сформулировали требование → реализовали → посмотрели результат → заметили проблему → уточнили задачу → исправили и проверили**.

## 16. Как использовали AI и что проверяли самостоятельно

AI-агент использовался как инструмент разработки, а не как основание считать задачу выполненной без проверки. Для Codex формулировались конкретные этапы с границами работ и запретами на ненужные изменения. Отдельно требовали соблюдать ООП/SOLID без лишних абстракций, запускать тесты, сохранять API-контракты и оформлять изменения через Git.

По ответам Codex сверяли выполненные изменения, результаты сборки, файлы и PR. Там, где проверка обнаруживала проблему — CORS, ещё не завершённый этап, неудобное модальное окно, сдвигающиеся блоки — формулировали дополнительное требование и исправляли. Полная выгрузка технической сессии и хронология коммитов служат более точными источниками времени и последовательности, чем пересказ в этом документе.
